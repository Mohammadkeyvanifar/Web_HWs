سوال اول :
Git merge زمانی کاربرد دارد که شما داری روی یه پروژه واحد کاری انجام میدی و یه بخشی از پروژه رو جدا میکند (یعنی یه کپی از کد میگیرد و روی شاخه ای که ایجاد کرده شروع میکنی اون قسمت از کدی که میخوای توسعه بدی رو روی ان انجام میدی) و بعد از اعمال تغییرات با زدن git merge  میاد و اون شاخه رو به شاخه اصلی پروژه اعمال میکند که این یعنی این ادم خاص روی این شاخه اصلی در این زمان و اگر بخواهد روی ان کامنت و توضیحات هم میگذارد میگذارد و به پروژه اصلی اعمال میشود

Git rebase یعنی ان شاخه تمام تاریخچه رو حذف میکند و به این معنی است که انگار این پروژه هیچ تاریخچه ای ندارد و انگار که پروژه ای است که هیچ تغییراتی روی ان اعکال نشده و اماده ی تغییرات است. هیچ کدی اضافه هو حذف نمیشود فقط تاریخچه را تمیز میکند .


سوال دوم : 
اولین چیزی که خیلی مهم بدونیم hunk  هستش که یعنی کل تغییراتی که داخل پروژه اعمال کردی رو به صورت بخش بخش میکنه. جوری که متوجه میشویم این تغییرات کد کجای کد اصلی قرار دارد . 
و خب ما میتوانیم با استفاده از دستور git add –p این تغییرات رو به صورت دانه دانه به ما نشان بدهد که ما از بین ان ها یا ان ها را yes  یا no  که یعنی یا تغییرات رو تایید میکنیم که اعمال بشه یا انقدر تغییر بزرگ است که نیاز داریم همان تغییر دوباره قسمت قسمت بشود که با split  استفاده میکنیم . 
و خب یکی از فواید ان این است که وقتی هم یه قسمت کد رو دیباگ کردی و همین طور یه توانایی جدید به کد اضافه کردی میتونی این دو تا رو تمیز بدی با استفاده از git add –p و ان ها را اضافه بکنی یا نه به صورت مستقیم با زدن این دستور git add  انجام بدی .

سوال سوم : 
git bisect یک توانمندی گیت هستش که به ما کمک میکند که بتوانیم عیب یابی بکنیم بین commit هایی که کردیم .
روندی که کار میکند به این شکل هستش که با زدن این دستور git bisect start میگویی که میخواهم جست و جو را شروع کنی و بعد git bisect bad را میزنیم که نشان میدهد نسخه فعلی مشکل دارد. و بعدش با زدن این دستور git bisect good  و نشان مشخص کردن ادرس کامیت سالم نشام میدهیم که  از اینجا به بعد کامیت مورد دار هست و حالا گیت می اید به صورت سرچ باینری در کمتری زمان پیدا میکند که کدام کامیت ایجاد خرابی است. اگر ما بخوایم که بین 1000 کامیتی که کردیم و حالا مشکل برخوردیم و میخوایم پیدا کنیم اگر خودمون بخوایم این کار رو بکنیم روز ها طول میکشد ولی وقتی از امکانات گیت استفاده کنیم در کمترین زمان یعنی چند ثانیه گیت مورد دار را پیدا میکند .

سوال چهارم : 
بخش اول : 
git status : با این دستور نشان میدهد که چه چیز هایی و چه چیز هایی در stage  قرار دارد یا خیر.
git diff : تغییراتی را نشان میدهد که هنوز وارد stage نشده اند یعنی همان تغییرات جدیدی که بعد از git add انجام دادیم . 
git diff –staged : تغییراتی که در stage قرار دارند و اماده کامیت هستند 
کلا یه سری ها در stage قرار دارند یعنی اماده کامیت کردن است و ان هایی که قرار ندارند اماده کامیت نیستند .

بخش دوم : 
همه تغییراتی که در stage قرار دارند کامیت میشوند و اگر وجود نداشت کامیت نمیشود حتی ان فایل هایی که بعد از وارد stage شدن باز هم در ان ها تغییرات اعمال کردیم .

بخش سوم : 
باید یک فایل با نام .gitignore بسازی یا وجود دارد . بعد پوشه /tmp رو داخلش قرار میدی و ان وقت گیت هاب به صورت خودکار اصلا فایل های داخل این پوشه را نادیده میگیرد. 
این کار برای فایل هایی که قبلا Track شده اند انجام میشود روی فای هایی که گیت نمیشناسد و نظارتی روی ان ها ندارد این عمل تاثیری ندارد . برای اینکه بتوان این کار را کرد باید از حالت Track خارج کنی و بعد روی ان اعمال میشود 

سوال پنجم : 
بخش اول : 
Conflict زمانی رخ میدهد که همزمان دو نفر روی یک نقطه مشترک کد بخواهند تغییرات اعمال کنند . اگر دو نفری که دارند تغییرات اعمال میکنند روی یه نقطه مشترک نباشد خوده گیت انهارا میگذارد به صورت جداگانه و بدون conflict رخ نمیدهد .
مانند سیستم عامل که میخواهند روی یک سورس مشترک چیزی بنویسند . ولی خب در گیت هاب میپرسد که کدام اولویت دارد 
بحش دوم : 
با زدن دستور git status ان هایی که با هم تداخل دارند را نشان میدهد با رنگ قرمز و بعد از باز کردن ان ها و دیدن Conflict Markers کامل متوجه میشوید که کدام قسمت دقیقا تداخل ایجاد شده است .
بخش سوم : 
به صورت دستی ان قسمت ها را با هم درست میکنیم و بعدش دوباره git status را میزنیم تا اگر مشکلی داشت دوباره میریم و دستی درستش میکنیم اگر هم که وجود نداشت همان را کامیت میکنیم  
ابتدا در یک ویرایشگر کد ان را اصلاح میکنیم 
git add README.md با زدن این دستور ان را اضافه میکنیم. 
بعد دوباره با git status دوباره چک میکنیم 
و اگر هنوز درست نشده بود دوباره این روند رو تکرار میکنیم 
بخش چهارم : 
git merge –abort با این دستور به یک پله قبل از مرج برمیگردیم انگار که هیچ اتفاقی نی افتاده است .



سوال ششم : 
بخش اول : 
با زدن این دستور git checkout -- notes.txt تمام تغییراتی که در فایل notes.txt وجود داشته حذف میشود 
Working tree : تغییرات پاک شده و به حالت قبلی برمیگردد
Stagfing area : چون تغییرات اصلاً به Staging نرفته بودند پس تغییری نمی‌کند 
Commit history : تاریخچه کامیت‌ها دست‌نخورده باقی می‌ماند.
بخش دوم : 
با زدن این دستور git restore --staged notes.txt فقط unstage مشود . 
Working tree : کدهای شما سالم و دست‌نخورده در فایل باقی می‌مانند.
Staging area : فایل از حالت آماده‌ی کامیت خارج می‌شود به حالت Unstaged برمی‌گردد
Commit history : تاریخچه کامیت‌ها هیچ تغییری نمی‌کند.
بخش سوم : 
با زدن این دستور git revert <commit-hash> و بجای <commit-hash> کد ان کامیت اشتباه را مینویسیم . این کار یه کامیت جدید میسازه و کامیت قبلی رو درست میکنه.
اگر force push کنیم میبینید تاریخچه stage  ها تغییر میکند و همگروهی ها conflict میخورند .
Working tree : بدون تغییر میماند 
Stage area : خالی میماند 
Commit history : هم کامیت قبلی باقی میماند هم کامیت جدید با تاریخ جدید ثبت میشود روی قبلی که باعث میشود که شرایط درست بشه.
